株式会社ミツワ電子器製作所 ウェブサイトの、制作完了から本番公開・請求・入金、公開後の運用までの工程をまとめたもの。
GitHub issue（#2〜#10）で管理していた内容をここに集約した（issue は 2026-11-20 に削除済み）。

## 全体フロー

```
STEP1-1 サイト全体のテスト ──┐
STEP1-2 A-15C 資料の反映   ──┴─▶ STEP2 本番サーバーへのアップロード
                                      │
                                      ▼
                              STEP3 本番内容の検収（依頼者OK）
                                      │
                                      ▼
                              STEP4 請求書のPDF送付
                                      │
                                      ▼
                              STEP5 入金確認

運用  修正・追加要望対応（公開後も継続）
```

- 支払いまでの流れ: 本番アップロード → 依頼者の検収OK → 請求書送付 → 入金。

## STEP1-1｜サイト全体のテスト ✅ 完了

**目的**: 本番公開の前に、サイト全体の表示と動作を確認する。

### 確認項目と結果

| 品質軸（壊れると何が起きるか） | 確認項目 | 結果 |
|---|---|---|
| 見た目: レイアウト崩れで信頼を損なう | 全ページの表示崩れ（トップ／プライバシー／サンクス） | ✅ |
| 導線: リンク切れで目的のページに着けない | ヘッダー・フッター・内部リンクのリンク切れ | ✅ |
| 問い合わせ: 送れなければ商談機会を失う | フォームのクライアント検証（必須項目・送信ブロック・ハニーポット） | ✅ |
| 環境差: 相手の端末やブラウザで再現するか | レスポンシブ（スマホ／タブレット／PC） | ✅ |
| 〃 | 主要ブラウザ（Chrome / Safari / Edge） | ✅（Edge はオーナー判断で省略） |
| コンテンツ資産: 製品情報を見られる・入手できるか | 画像・PDFの表示とダウンロード | ✅ |
| 発見性: 検索やSNSで正しく表示されるか | メタ情報（title / description / OGP） | ✅ |
| 問い合わせ | フォームの実メール到達 | ⏭️ STEP2 タスク6で実施 |

詳しい結果は [`specification/website/test-report-issue-3.md`](../../specification/website/test-report-issue-3.md) に記録してある。

### この項目で足りる理由
- サイトは Vite で出力する静的HTMLで、サーバー側の処理、ログイン、動的データ、負荷の変動がない。そのため、入力検証・DB・認証・負荷試験といった Web アプリ向けのテストは対象外にした。
- 問い合わせの受付は外部サービス（FormSubmit）に任せているので、こちらの責任範囲は「送信が届くか」の確認だけになる。
- 本番環境でしか確かめられない項目（`BASE_PATH` / `SITE_URL` での再ビルド、robots / sitemap、FormSubmit の有効化）は STEP2 で扱う。

## STEP2｜本番サーバーへのアップロード

**目的**: 確認と反映が済んだサイトを、ミツワ電子器製作所の本番サーバーにアップロードする。

**前提**: STEP1-1 と STEP1-2 が完了していること。

今のビルドは GitHub Pages（`https://asaty94.github.io/website-mitsuwa/`）のサブパス向けになっている。本番サーバーはドメイン直下から配信するので、このままのファイルでは画像・リンク・SEO情報・フォーム送信後の遷移が壊れる。以下の手順で本番向けに作り直す。

### 1. 本番用にビルドする
```sh
cd website
BASE_PATH=/ SITE_URL=https://本番ドメイン/ npx vite build
```
- **必要な理由**: 既定のビルドは `base=/website-mitsuwa/` を前提にしている。パスが `/website-mitsuwa/...` のままだと、本番では画像・CSS・リンクが 404 になる。
- **これで足りる理由**: `BASE_PATH=/` でアセットパスの接頭辞が直る。`SITE_URL` を指定すると、`website/vite.config.js` の `publicBasePlugin` が HTML 内の絶対URL（canonical / og:url / フォームの `_next`）を本番ドメインに置き換える。

### 2. `website/public/robots.txt` の URL を手で書き換える
- **必要な理由**: `public/` 配下は Vite が変換しないので、`SITE_URL` による置換が効かない。今の `Sitemap: https://asaty94.github.io/website-mitsuwa/sitemap.xml` のままだと、クローラに間違ったサイトマップの場所を伝えてしまう。
- **これで足りる理由**: robots.txt に書かれている URL は Sitemap 行だけ。

### 3. `website/public/sitemap.xml` の URL を手で書き換える
- **必要な理由**: 理由は 2 と同じ。`<loc>` が GitHub Pages の URL のままだと、本番とは別ドメインの URL が検索エンジンに登録されてしまう。
- **これで足りる理由**: `<loc>` は 2 件（トップとプライバシーポリシー）だけ。

### 4. FormSubmit のメールを有効化し、`form action` を発行されたエイリアスに差し替える
現状: `website/src/index.html:126` の `action="https://formsubmit.co/mitsuwa@iris.eonet.ne.jp"`

- **必要な理由**:
  - FormSubmit は、メールアドレス宛ての最初の送信で届く確認メールを承認しないと有効にならない。有効化しないままだと、本番でフォームを送信してもメールが届かない。
  - `action` にメールアドレスがそのまま書かれていると、スパム業者に収集される。有効化後に発行されるランダムなエイリアス（例: `https://formsubmit.co/xxxxxxxx`）に差し替えれば、送信先はそのままでアドレスを隠せる。
- **これで足りる理由**: CSP の `form-action` は `https://formsubmit.co` を許可済み（`website/src/index.html:8` ほか）。エイリアスも同じドメインなのでブロックされない。`_next` の遷移先はタスク1の置換で本番の `thanks.html` になる。

### 5. `website/dist/` を FTP/SFTP で本番サーバーにアップロードする
- 静的HTMLだけの構成なので、`dist/` 一式を置けば動く。

### 6. 本番URLで表示と動作を確認する
- [ ] 表示崩れ・リンク切れ・画像/PDF・SEOメタ（canonical / og:url）
- [ ] **フォームの実送信テスト**（STEP1-1 から持ち越した項目。タスク4の完了が前提）
  1. 本番URLのフォームからテスト内容を 1 件送信する
  2. `mitsuwa@iris.eonet.ne.jp` に問い合わせメールが届くか確認する
  3. 送信後に本番ドメインの `thanks.html` へ遷移するか確認する（`_next` が本番URLになっているか）
  4. 迷惑メールに振り分けられていないか、文字化けがないかを確認する
- 到達確認には FormSubmit の有効化・エイリアス・本番ドメインの `_next` の 3 つが揃っている必要があるので、プレビューではなく本番に移した後に行う。
