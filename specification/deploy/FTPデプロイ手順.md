> ⚠️ **このリポジトリはパブリックです。**
> このファイルには **手順だけ** を書き、次の情報は書かないでください。

## 1. 確認用公開（GitHub Pages）

1. 作業ブランチで修正し、PR を作成して `main` にマージする
2. `.github/workflows/deploy.yml` が自動で実行され、GitHub Pages に反映される
   - 進み具合は GitHub リポジトリの **Actions** タブで確認できる
3. 反映を確認したら、依頼者に URL を連絡して確認してもらう

### 依頼者に確認をお願いするときに伝えること

- 確認用の URL
- 今回の変更点
- 確認してほしいポイント（文言・写真・資料などの内容の間違い）。依頼者は IT に詳しくないため、専門用語を使わず、表示やリンクの動作など技術的な確認はこちらで行う
- PC とスマートフォンの両方で見てほしいこと

### 承認の記録

依頼者から OK をもらったら、下の「[公開履歴](#公開履歴)」に日付と内容を記録する。

## 2. 本番公開（レンタルサーバーへの FTP アップロード）

### 2-1. 事前準備（初回のみ）

仮の HTML を置いて、FTP で接続でき、公開ディレクトリのファイルを更新できることは確認済み。独自ドメインがサーバーに紐づいていることも確認済み。残りの項目は、本番のアップロードの前に確認する。

- [x] 依頼者から FTP の接続情報を受け取る
- [x] FTP クライアントをインストールする（FileZilla、Cyberduck など）
- [x] 公開ディレクトリ（レンタルサーバーによって `public_html`、`www`、`htdocs` などの名前）を確認する
- [x] 独自ドメインがサーバーに紐づいているか確認する
- [ ] 接続情報をパスワード管理ツールに登録し、下の「[接続情報の管理](#接続情報の管理)」の項目名を記入する
- [ ] 前回の接続方式が **FTPS（FTP over TLS）** か **SFTP** だったかを確認する。通常の FTP だった場合は、レンタルサーバーが FTPS・SFTP に対応しているか確認する
  - 対応していれば必ず使う。暗号化しない通常の FTP では、パスワードが平文のままネットワークを流れる
- [ ] 仮の HTML を `https://（本番ドメイン）/` で開き、HTTPS で表示できる（ブラウザに鍵マークが出る）ことを確認する。出なければ、レンタルサーバーの管理画面で SSL を有効にする
- [ ] 確認のために置いた仮の HTML を、本番のアップロードのときに削除する

### 2-2. 本番用の設定変更（初回・ドメインを変えたときのみ）

ビルドしても自動では置き換わらないファイルは、手で書き換える。

| ファイル | 変更内容 |
| --- | --- |
| `website/public/robots.txt` | `Sitemap:` の URL を本番ドメインにする |
| `website/public/sitemap.xml` | すべての `<loc>` を本番ドメインにする |

> `canonical` / `og:url` / `og:image` は、ビルド時に `SITE_URL` で自動的に置き換わる（`website/vite.config.js` を参照）。
>
> ⚠️ `robots.txt` と `sitemap.xml` を本番用に書き換えて `main` にマージすると、GitHub Pages 側も本番の URL を指すようになる。依頼者の確認期間中は、本番用の書き換えを別ブランチに置いておくなど注意する。

### 2-3. 本番用ビルド

```bash
cd website
npm ci
BASE_PATH=/ SITE_URL=https://（本番ドメイン）/ npx vite build
```

- ドメイン直下ではなくサブディレクトリに置く場合は、`BASE_PATH=/subdir/`、`SITE_URL=https://（本番ドメイン）/subdir/` のように指定する
- 出力先は `website/dist/`

ローカルで表示を確認する：

```bash
BASE_PATH=/ npx vite preview
```

### 2-4. FTP でアップロード

1. パスワード管理ツールから接続情報（ホスト・ユーザー名・パスワード・公開ディレクトリ）を確認する
2. FTP クライアントで接続する
   - 接続方式は **FTPS（明示的な FTP over TLS）** か **SFTP** を選ぶ
   - FTP クライアントに接続先を保存する場合は、パスワードがマスターパスワードや OS のキーチェーンで保護される設定にする
3. **公開ディレクトリに入ったことを確認してから**、`website/dist/` の **中身**（`dist` フォルダそのものではない）をアップロードする
4. 2 回目以降は、ファイルを上書きする
   - ファイル名が変わったもの（ビルドで生成される `assets/` 内のファイルなど）は古いものが残るので、不要になったファイルは削除する
   - レンタルサーバーがはじめから置いているファイル（`.htaccess` など）は消さない

### 2-5. 公開後のチェックリスト

[`サイトのテスト.md` の「3. 本番環境：公開後のテスト」](../website/サイトのテスト.md#3-本番環境公開後のテストstep5)の項目を確かめ、結果を同じ節に書く。

### 2-6. 本番公開後の GitHub Pages の扱い

確認用サイトが残ったままだと、検索エンジンに同じ内容のサイトが 2 つあると見なされることがある。本番公開後は次のどちらかにする（依頼者と相談する）。

- GitHub Pages を停止する（Settings → Pages）
- 今後の修正の確認用として残す場合は、`noindex` を付けるなどして検索結果に出ないようにする

## 接続情報の管理

| 情報 | 保存場所 |
| --- | --- |
| FTP ホスト・ポート・接続方式・ユーザー名・パスワード | パスワード管理ツール（項目名: `（項目名を記入）`） |
| 公開ディレクトリのパス | 同上（メモ欄） |
| レンタルサーバーの会社名・管理画面の URL とログイン情報 | 同上（別項目） |
| 依頼者の担当者・連絡先 | 同上（メモ欄） |

ルール：

- **リポジトリには一切書かない**（`.gitignore` で除外したファイルにも書かない。誤ってコミットすると履歴に残るため）
- チャットやメールに平文でパスワードを書いて送らない。共有するときはパスワード管理ツールの共有機能を使う
- 将来 GitHub Actions で FTP アップロードを自動化する場合は、接続情報を **GitHub Secrets**（Settings → Secrets and variables → Actions）に登録する
- 依頼者との契約が終わったら、依頼者に FTP パスワードの変更をお願いする
